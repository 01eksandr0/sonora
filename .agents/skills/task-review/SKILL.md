# Скіл: Авторев'ю задачі (Task Review)

Цей скіл автоматизує повний цикл рев'ю коду для задач проекту **Sonora**: перевірку гілки, створення PR/MR з описом виконаних робіт, аналіз коду за 6 ключовими критеріями якості та публікацію структурованого авторев'ю на GitHub.

---

## Робочий процес (Workflow)

```mermaid
graph TD
    A[Отримати запит на рев'ю задачі №] --> B[Перевірити гілку task-{номер}]
    B -->|Гілки немає| C[Створити гілку task-{номер} та за комітити зміни]
    B -->|Гілка є| D[Перевірити незбережені зміни]
    C --> E[Зробити git push -u origin task-{номер}]
    D --> E
    E --> F[Перевірити / створити PR з описом задачі]
    F --> G[Запустити автоматичні перевірки build / test / lint]
    G --> H[Провести детальний Code Review диффу]
    H --> I[Сформувати звіт за рівнями критичності]
    I --> J[Опублікувати авторев'ю коментарем у PR на GitHub]
```

## Етап 1. Перевірка гілки та створення PR

1. **Визначення номера задачі**:
   - Номер береться з запиту користувача (наприклад, `15`, `03`, `27`) або з назви поточної гілки.
2. **Перевірка поточної гілки**:
   ```bash
   git branch --show-current
   ```
   - Якщо назва поточної гілки **не** `task-{номер}`:
     - Перевірити, чи існує гілка `task-{номер}`:
       ```bash
       git branch --list "task-{номер}"
       ```
     - Якщо гілка вже існує — переключитися на неї:
       ```bash
       git checkout task-{номер}
       ```
     - Якщо гілки немає — створити її та перейти:
       ```bash
       git checkout -b task-{номер}
       ```
3. **Коміт змін (якщо є незакомічені файли)**:
   ```bash
   git status
   ```
   - Якщо є змінені або нові файли:
     ```bash
     git add .
     git commit -m "feat(task-{номер}): implement task {номер} changes"
     ```
4. **Пуш гілки у віддалений репозиторій**:
   ```bash
   git push -u origin task-{номер}
   ```
5. **Створення Pull / Merge Request з описом робіт**:
   - Перевірити, чи вже відкрито PR для гілки `task-{номер}`.
   - Сформувати змістовний опис того, що було зроблено в задачі:
     - Огляд реалізованого функціоналу.
     - Зміни на бекенді (`apps/api`), фронтенді (`apps/web`), у базі даних (`prisma/schema.prisma`) та спільних пакетах (`packages/*`).
     - Додані тести.
   - Якщо встановлено `gh` (GitHub CLI):
     ```bash
     gh pr create --title "feat(task-{номер}): [Коротка назва задачі]" --body "[Детальний опис реалізованих змін]"
     ```
   - Якщо `gh` не встановлено або не авторизовано:
     - Надати користувачу пряме посилання для створення PR:
       `https://github.com/01eksandr0/sonora/pull/new/task-{номер}`
     - Вивести сформований заголовок та опис для вставки.

## Етап 2. Автоматичні перевірки якості (Automated Quality Gates)

Перед ручним аналізом коду обов'язково виконати автоматичні інструменти:

1. **Перевірка типів та компіляція**:
   ```bash
   pnpm -r build
   ```
2. **Запуск юніт та інтеграційних тестів**:
   ```bash
   pnpm -r test
   ```
3. **Перевірка лінтера**:
   ```bash
   pnpm -r lint
   ```
4. **Перевірка форматування**:
   ```bash
   pnpm format:check
   ```

Результати перевірок обов'язково включаються у фінальний звіт авторев'ю.

## Етап 3. Комплексний аналіз коду (Code Review)

Отримати diff змін відносно базової гілки (`main`):

```bash
git diff origin/main...HEAD
```

Проаналізувати кожну зміну за **6 критеріями**:

### 1. Best Practices (Кращі практики)

- **Бекенд (NestJS)**:
  - Правильне використання модулів, контролерів і провайдерів.
  - Валідація вхідних даних через DTO з декораторами `class-validator` та Swagger (`@ApiProperty`).
  - Відсутність витоку Prisma-сутностей у відповіді клієнту (мапінг у Response DTO).
  - Транзакційність для взаємопов'язаних операцій (`prisma.$transaction`).
  - Безпека: захист роутів (`@UseGuards(JwtAuthGuard)`), отримання поточного користувача через `@CurrentUser()`.
- **Фронтенд (Vue 3 / FSD)**:
  - Суворе дотримання шарів FSD (`shared ← entities ← features ← widgets ← pages ← app`).
  - Використання Composition API (`<script setup lang="ts">`).
  - Чітке розмежування стейту: Server state у **TanStack Query**, Client/UI state у **Pinia**.
  - Коректна типізація пропсів та подій (`defineProps<{...}>()`, `defineEmits<{...}>()`).
- **Монорепозиторій**:
  - Спільні типи винесені у `packages/shared-types`.
  - Відсутність циклічних залежностей між пакетами.

### 2. Naming Conventions (Неймінг)

- Зрозумілі, точні назви функцій, змінних, класів та інтерфейсів.
- Консистентність стилів найменування:
  - PascalCase для компонентів Vue, класів, DTO, TypeScript типів/інтерфейсів.
  - camelCase для функцій, методів, змінних, composables (`use*`).
  - kebab-case для файлів у FSD і NestJS (`landing-page.vue`, `auth.service.ts`).
  - UPPER_SNAKE_CASE для констант.
- Відповідність термінології домену з [ROADMAP.md](../../../ROADMAP.md) (`DeezerTrack`, `MusicProvider`, `TasteProfile` тощо).

### 3. Logic & Correctness (Логіка та коректність)

- Чи повністю код вирішує поставлену бізнес-задачу з роадмапу?
- Чи немає логічних помилок, помилок на одиницю (off-by-one), безкінечних циклів?
- Чи правильно обробляються асинхронні виклики (`async/await`, відсутність unhandled rejections)?
- Ідемпотентність операцій, які мають бути ідемпотентними (наприклад, like/unlike, refresh токенів).

### 4. Edge Cases & Boundary Conditions (Граничні випадки)

- Обробка порожніх станів (пусті масиви треків, відсутність результатів пошуку).
- Nullable/undefined поля (наприклад, опціональні `previewUrl`, `avatarUrl`, `genres`).
- Помилки мережі та збої зовнішніх сервісів (Deezer API недоступний, таймаут, невалідний JSON).
- Граничні значення пагінації (`offset` більший за `total`, `limit <= 0`).
- Неавторизований або заборонений доступ (401 Unauthorized, 403 Forbidden).

### 5. Cleanliness & Reusability (Чистота та перевикористовуваність)

- Принцип DRY: відсутність дублювання коду, винесення спільної логіки в утиліти/компоненти.
- Принцип єдиної відповідальності (Single Responsibility): функції та компоненти не перевантажені зайвою логікою.
- Чистота коду: видалені `console.log`, закоментований мертвий код, невикористані імпорти.
- Самодокументований код без надлишкових очевидних коментарів.

### 6. Optimality & Method Selection (Оптимальність та ефективність)

- Оптимальність запитів до БД (відсутність N+1 запитів у Prisma, вибірковий `select`/`include`).
- Використання Redis кешу для "важких" або повторюваних запитів каталогу.
- Ефективність реактивності у Vue (уникати зайвих watchers, надлишкових глибоких спостережень).
- Оптимальний вибір методів стандартної бібліотеки (наприклад, `Set`/`Map` для швидкого пошуку замість вкладених `find`/`filter`).

## Етап 4. Формування звіту авторев'ю за рівнями критичності

Звіт обов'язково структурується за **чотирма рівнями критичності** (від найважливіших до опціональних):

1. 🔴 **Критично (Critical)**:
   - Вразливості безпеки, витік паролів/секретів.
   - Помилки, що ламають збірку або призводять до падіння додатку (runtime crash).
   - Втрата чи пошкодження даних у базі даних.
   - Порушення базової цілісності системи.
2. 🟠 **Потрібно виправити (Must fix)**:
   - Порушення бізнес-логіки задачі з роадмапу.
   - Необроблені граничні випадки (null pointer, невірна обробка 404/500).
   - Порушення архітектурних кордонів FSD або модулів NestJS.
   - Відсутність валідації вхідних даних або відсутність критичних тестів.
3. 🟡 **Можна виправити в майбутньому (Should fix / Tech debt)**:
   - Неоптимальні запити чи структури даних (кандидати на оптимізацію).
   - Можливості для кращого перевикористання коду (рефакторинг).
   - Покращення типізації (заміна `any`/неповних типів).
4. 🟢 **Не критично / Рекомендації (Nit / Suggestions)**:
   - Дрібні зауваження до неймінгу, форматування чи структури файлів.
   - Покращення коментарів та документації.
   - Стилістичні оптимізації.

## Етап 5. Публікація авторев'ю коментарем на GitHub

1. **Якщо доступний `gh` (GitHub CLI)**:
   - Опублікувати коментар безпосередньо у відкритий PR:
     ```bash
     gh pr comment <номер_pr_або_гілка> --body-file <шлях_до_файлу_звіту>
     ```
2. **Якщо `gh` недоступний**:
   - Зберегти копію звіту в файл: `reviews/task-{номер}-review.md`.
   - Вивести повний, відформатований текст авторев'ю у відповідь користувачу.
   - Надати пряме посилання на PR на GitHub для швидкої вставки коментаря.
